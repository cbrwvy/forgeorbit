# Owner signing setup

ForgeOrbit is a personal-use macOS application. Public Apple distribution requirements are not part of the product.

The trusted application is the copy you sign on this Mac with a certificate that stays in your login keychain. It is not a Developer ID build, and it is not notarized. Enrollment and provider execution stay closed until that certificate exists, the app and the embedded helper both verify against it, and you complete one macOS authentication yourself.

## What this identity is

The local Owner certificate is a self-signed code-signing certificate:

- Common name: **`ForgeOrbit Local Owner`**
- Store: the login keychain
- Private key: non-extractable, never written into the repository, never exported as a `.p12`
- Application identifier: **`app.forgeorbit`**
- Helper identifier: **`app.forgeorbit.owner-trust`**
- Trust anchor: the certificate's SHA-256, stored as a login-keychain item named `app.forgeorbit.local-owner-anchor`

There is no TeamIdentifier. ForgeOrbit does not invent one. `TeamIdentifier=not set` on this certificate is expected. `Signature=adhoc` is not this identity.

The certificate is deliberately **not** added to the macOS trust store. `security find-identity -v -p codesigning` therefore reports `0 valid identities` even after you create it; that is expected, not a failure. Use `security find-identity -p codesigning` (without `-v`) or `bun scripts/local-owner-identity.ts --status` to see it. Signing selects the exact certificate whose leaf SHA-256 equals the login-keychain anchor, by SHA-1, with `codesign --keychain <login>`. A common name alone is never enough.

A QA build stays `app.forgeorbit.qa` / `app.forgeorbit.qa.owner-trust`. Signing that bundle with the Owner certificate is refused. A disposable test certificate named `ForgeOrbit Test Signing Fixture` is not the Owner anchor.

## Key generation and what is proven

The identity is generated by `scripts/local-owner-identity.ts` from an interactive Terminal. The private key is written to a `0700` temporary directory, encrypted with a random passphrase that stays in process memory, packed into a PKCS#12 with a second random passphrase, imported with `security import -x`, and the temporary files are overwritten and removed in a `finally` block.

What this proves:

- The private key file is encrypted at rest for the short time it exists, and its directory is not group/world readable.
- The passphrases are random and are never printed, logged, stored, or committed.
- The Keychain import is performed with `-x`, which asks the Keychain to mark the private key non-extractable after import.

What this does **not** prove: that the key was never extractable at any point. The key material demonstrably exists before the import, and on this macOS a direct `SecKeyCopyExternalRepresentation` / `SecItemExport` probe could not independently confirm the `-x` attribute (legacy keychain RSA keys reject those exports for unrelated reasons). Treat the Keychain key as non-exportable by policy and by the `-x` request, not as cryptographically proven non-extractable. The key never leaves the login keychain in normal operation.

## Keychain prompts and narrow signing consent

The sign script does **not** grant codesign permanent access. It does not pass `-T /usr/bin/codesign`, does not run `security set-key-partition-list`, and does not ask you to choose **Always Allow**.

macOS asks for the private key **once per signature operation**, not once per process. Signing every nested Mach-O with the Owner identity therefore opens one dialog per file — 63 dialogs on the current ForgeOrbit bundle. That is why an earlier build appeared to ask forever: it was progressing one file at a time.

The signer now touches the Owner key **exactly twice**:

1. the helper (`app.forgeorbit.owner-trust`), and
2. the application bundle, which signs the main executable and seals all nested code.

Every other Mach-O file and nested bundle (Bun, tmux, Chrome for Testing, the notifier, helpers, frameworks) is re-signed **ad-hoc** in one pass. Ad-hoc signing uses no private key, so it opens no dialog, and `--preserve-metadata=entitlements` keeps their entitlements. Nested code is still sealed by the Owner-signed application, so modifying it breaks verification; it simply cannot present Owner authority itself.

Expect **two** Keychain dialogs, one after the other. Answer **Allow** for each. Do not choose **Always Allow**.

Why this matters: if codesign (or any application) is permanently trusted for that key, any process running as you can run `codesign -s <pinned SHA-1> --keychain login` and produce a bundle signed by the same pinned certificate. ForgeOrbit's verifier would accept that bundle's identity. Permanent access turns a one-time Owner confirmation into an ambient signing capability. The per-operation Owner prompt is the signing gate.

## What a self-signed certificate does and does not guarantee

It does:

- Give every rebuild the same designated requirement, so the signature can be checked against one certificate instead of accepting any ad-hoc seal.
- Keep the signing identity and its private key in the login keychain, so a rebuild does not need a new certificate.
- Make a modified or replaced helper fail `codesign --verify --strict`.
- Preserve nested entitlements on re-signing, because the signer passes `--preserve-metadata=entitlements`. Without that flag a re-sign silently strips JIT/library-validation entitlements from vendored binaries.
- Keep the Owner identity on the two components that actually assert it (application and helper) while nested third-party code stays ad-hoc. The application seal still protects nested code integrity.

It does not:

- Make Gatekeeper treat the app as an identified developer.
- Provide Apple notarization, OCSP revocation, or a Developer ID chain of trust.
- Stop a process that is already you, with your login keychain unlocked, from replacing the anchor item or importing a different certificate. The anchor item is created with `-A` (any application may read it) because it is a public fingerprint, not a secret; reading it grants no authority. `-A` does not make replacement easier — the account owner can always rewrite the item. The protection after enrollment is the fingerprint stored on the enrollment row plus the Secure Enclave proof, not the item's ACL.
- Bind the Secure Enclave key itself to this certificate. The P-256 key is protected by Secure Enclave user presence (`biometry` or the Mac password), not by the bundle's code signature. Any process running as you that asks for that key tag can trigger a presence prompt; it cannot make ForgeOrbit accept the resulting proof unless it is also the pinned application. After enrollment, a bundle signed by a different certificate is refused, and the enrollment stays pinned to the old fingerprint.
- Make the trust logic immutable. The verification code lives in this repository. An AI agent with write access can change `signing-policy.ts`, `identity.ts`, `service.ts`, or the Swift helper, but it still cannot install a trusted build without the Owner's Keychain confirmation for the signing key. The Owner's per-signing prompt — not the repository — is the boundary. Review signing-related diffs before signing.
- Survive a deliberately replaced certificate without an explicit Owner action. While an enrollment is active, a different certificate cannot enroll or rotate it. After the Owner explicitly revokes that enrollment, a fresh Secure Enclave key can enroll under the new certificate; the revoked key stays revoked.

LocalAuthentication by itself is not approval. The helper still has to be the embedded, pinned binary, and the signature still has to match one exact operation.

## Create the identity

Run this yourself in Terminal. An agent session is refused because it is not an interactive terminal. The command does not create the identity unless both flags are present.

```sh
bun scripts/local-owner-identity.ts --create --confirm-owner-action
```

macOS may ask before the key is imported. Allow that only if you are creating this identity. If the identity already exists, the command prints the fingerprint and does not replace it.

Replacing it is a separate, explicit action. An existing enrollment stays pinned to the previous certificate and becomes unusable for new authority. Revoke that enrollment in the Owner UI first, then enroll again; a new enrollment always creates a fresh Secure Enclave key, and the revoked key stays revoked:

```sh
bun scripts/local-owner-identity.ts --create --confirm-owner-action --replace-anchor --confirm-replace-local-owner-anchor
```

Check what is present without printing a private key:

```sh
bun scripts/signing-preflight.ts
bun scripts/local-owner-identity.ts --status
security find-identity -p codesigning
```

`productionSigning` is `owner-action-required` until the certificate and the anchor fingerprint match. `developerIdRequired` and `notarizationRequired` are false. `--status` reports `present`, `certificateCount`, `anchorPresent`, and `anchorMatchesCertificate`.

If `codesign` reports `no identity found`, the certificate is not in the keychain search list or the anchor does not match the certificate. Run `bun scripts/local-owner-identity.ts --status`; the sign script fails closed rather than signing with another certificate.

## Build, then sign

`bun run build:local` still produces the ad-hoc `app.forgeorbit` bundle. That bundle is not the Owner identity. Build it, quit any running ForgeOrbit, and sign the built bundle. Follow the canonical [Personal Mac Update & Rollback Checklist](personal-update-checklist.md) for pre-upgrade snapshot/backup, full quit verification, staging, replacement, first launch, and rollback; do not replace `~/Applications/ForgeOrbit.app` until you have verified the signature and completed those pre-upgrade steps.

```sh
bun scripts/sign-macos-app.ts --app=build/local/ForgeOrbit.app --channel=local-owner
```

The script signs nested code from the inside out, then the Owner helper as `app.forgeorbit.owner-trust`, then the application as `app.forgeorbit`. Nested code is ad-hoc signed in one pass (no key access); the Owner key is used exactly twice — helper and application. Expect two Keychain dialogs and answer **Allow** for each, never **Always Allow**. Every invocation passes `--preserve-metadata=entitlements` so vendored Bun/Chromium entitlements survive the re-sign. Before any signature it resolves the certificate whose SHA-256 equals the login-keychain anchor and passes `--keychain <login>` plus that certificate's SHA-1 to `codesign`; a common name alone never selects the signing identity. If the anchor is missing or no certificate matches it, nothing is signed. The script does not use `codesign --deep`. It does not use a secure timestamp: Apple's timestamp server will not accept this certificate. It does not turn on the hardened runtime, because this Electrobun bundle has no tested hardened-runtime entitlements and a self-signed hardened runtime can prevent launch. `codesign --verify --strict` still has to succeed.

`--channel=qa` cannot use `ForgeOrbit Local Owner`. `--identity=-` and a Developer ID name are refused for `local-owner`.

## Verify

```sh
bun scripts/verify-local-owner.ts --app=build/local/ForgeOrbit.app
codesign -dv --verbose=4 build/local/ForgeOrbit.app
codesign -dv --verbose=4 build/local/ForgeOrbit.app/Contents/Resources/app/bin/forgeorbit-owner-trust
codesign --verify --strict --verbose=2 build/local/ForgeOrbit.app
codesign --verify --strict --verbose=2 build/local/ForgeOrbit.app/Contents/Resources/app/bin/forgeorbit-owner-trust
```

Expect bundle id `app.forgeorbit`, helper id `app.forgeorbit.owner-trust`, `Authority=ForgeOrbit Local Owner`, the same certificate SHA-256 on both, and `TeamIdentifier=not set`. A passing verification is not enrollment and does not start a provider.

## Enrollment

1. Launch the signed `app.forgeorbit` build.
2. Open the task or mission. Mission Control shows the operation read from the local database.
3. Choose the review action. The embedded helper shows the same operation.
4. Cancel creates no grant and no key.
5. Confirm only when you intend to enroll. macOS LocalAuthentication then runs. ForgeOrbit does not ask you to type the Mac password into the app.
6. The Secure Enclave creates a non-exportable P-256 key with user-presence access control. CryptoKit returns an SE-encrypted `dataRepresentation` blob (not the private key), which the helper stores in the app profile at `owner-trust/owner-se-key.bin` with mode 0600 and restores on later operations. It is machine-bound and unusable without Touch ID on this Mac. This blob exists because a self-signed app cannot use the keychain key item (`errSecMissingEntitlement`); no Apple entitlement is required for the CryptoKit key.
7. The backend stores the public key and the signing-certificate fingerprint only after the helper identity and the signature both verify.
8. A later review signs one fresh challenge for one exact operation. The grant is consumed once. Router eligibility, the registered account, the sandbox, the budget, and emergency stop still apply.

A QA build, an ad-hoc build, a different certificate, and a restored database cannot enroll as the Owner. A software key is not accepted in place of the Secure Enclave key. A cancelled enrollment creates no authority.

## What stays disabled until you finish those steps

Until the local Owner signature and one completed Owner authentication both exist:

- Enrollment stays closed.
- `executionReady` stays false.
- Codex and Claude are not started.
- Cursor and DeepSeek stay blocked.
- Opening Settings, AI Resources, Analytics, or Forecasts does not authenticate and does not start a provider.

The historical bundle id `app.forgeorbit.legacy` is not the current bundle id. It is not renamed and its Keychain items are not migrated.
