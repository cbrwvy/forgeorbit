# Usage analytics and forecasts

The **Analytics** workspace entry contains AI Resources, Forecasts, and Analytics. A Backlog card opens a task estimate. Analytics opens the recorded run breakdown and the estimate frozen for that task. The UI labels these views in English and Russian.

## Account and quota evidence

AI Resources uses AccountCore’s registered accounts and quota journal, with model and readiness information from Router 2.0. A configured account label and cached CLI authentication do not verify a provider subject. Current verified readings, historical readings, local observations, configured limits, and Unknown values retain distinct labels. Each observation keeps its native unit, window, observation time, and any evidenced reset. Different windows and accounts are never added together to claim remaining capacity. Harness meters stay separate from registered accounts.

The existing [FO-009F quota boundary](../qa/fo-009f-verified-quota01-results.md) still applies. Reading analytics never refreshes a provider, reads credentials, or starts a CLI. The Cursor organization adapter is implemented but not registered in production. See [AI resource evidence](ai-resource-evidence.md) for Owner-reported revisions, supported sources and exact quota matching. A quota balance alone cannot establish how much a task consumes. Subscription quota consumption stays Unknown when the runtime lacks a trustworthy, per-run measurement or conversion.

## Forecasts

The Forecasts view and Backlog task dialog use the same `forecast-v2` service. Inputs include the task prompt and acceptance criteria, task category, dependencies, project technology signals, active project rules, selected Developer resource, Reviewer requirements and stored execution evidence. The service reads manifest names and stores a digest of the rules without persisting their text in the forecast. A forecast calculates locally and leaves the task in Backlog.

A resource cohort matches project, technology, category, complexity, role, provider, harness, model, account and execution mode. When enough outcomes match the assigned Developer, that cohort takes precedence. A successful stage contributes at most one observation per completed task. Reviewer evidence requires a linked PASS. Synthetic and ambiguous runs cannot calibrate forecasts. Three comparable completed outcomes are required for the 25th, 50th and 85th percentile scenarios. The ranges describe observed uncertainty. Run intervals include any tool or provider waits the runtime cannot measure separately. Compatible completed outcomes can also calibrate test time, rework, run count and active wall time. Cold-start stages retain explicit heuristic ranges.

Group forecasts accept selected Backlog tasks, one or more projects, a cluster, or an approved mission. The scheduler expands tasks into the stages used by execution and QC. Developer and Reviewer turns occupy their own account, provider, and project slots. Developer turns also use the assigned specialist slot. An applicable cluster limit uses current registered membership. A separate local-test stage is included when the existing observed-test policy admits it or when comparable test evidence exists. It uses the local-test slot without claiming an AI account. Preparation is a separate stage. Its duration is measured only from a recorded start paired with completed, failed, or interrupted preparation. Waiting recorded inside that interval is reported separately and is not added to agent time. Without those events the duration stays Unknown. Completion remains a checkpoint with Unknown independent duration. Rework, repeated testing and final review are scenario stages. An active policy without a remaining rework grant removes those stages.

The dependency critical path leads through the predecessor task's completion checkpoint. An Owner gate can leave the calendar Unknown without consuming an AI slot. The expected schedule shows the resource keys and recorded planning bottlenecks by stage. The worker total sums Developer and Reviewer intervals. Active wall time takes their union. Resource delay is the difference from the free-slot scenario. An in-flight operation with no reliable release time can hold a slot in the constrained scenario. An explicit release assumption can free planning slots, while a selected live task still has an unresolved outcome. Paused, draining and recovering projects block the calendar. Forecasts never release runtime reservations.

### Capacity by pool and window

`capacity.ts` reads AccountCore definitions and observations. The same evidenced provider pool, scope, typed native unit and window share one capacity row across models and registered accounts. Independent definitions and windows keep separate balances. Alias observations from the same window use the lowest available remaining value. A mismatch in the evidenced period or reset, a conflict, or an expired observation prevents using that balance. The table labels verified, Owner-reported, configured, fixture and Unknown evidence. A comparable calculated API estimate can produce demand in minor units for supported same-currency API credit. Subscription meters have no trustworthy per-task demand conversion.

A plan totals known stage demand and separately counts stages with Unknown demand. Running work sharing a pool adds uncertainty when its remaining consumption is unmeasured. Current readings apply only within their evidenced horizon. The permissive scenario can place work after a recorded reset under an explicit assumption that the pool refills to its evidenced limit. The Owner can also provide up to eight future windows with a start, end, and allowance in the same native unit. Each stage's known demand is charged once per applicable typed pool. The planner checks each window against the resulting stage schedule and withholds a completion date when those assignments conflict. A bounded search can compare fastest, lowest comparable API charge, balanced, quota-preserving, and minimum expected resource wait. The search stops at a fixed node limit. A feasible result reached before that limit is optimal for the modeled inputs. A result found after the limit is the best feasible candidate and is not labeled globally optimal. Shared pools, account concurrency, dependencies, and existing reservations are inputs. Strict planning does not treat an assumed future reset as capacity. Strict planning excludes assumed allowances. A recorded reset is shown separately from all Owner assumptions. The ledger models local planning demand and creates no provider-side reservation.

### Resource alternatives and estimate revisions

Router 2.0 supplies availability, eligibility reasons and exact account bindings. The Owner can compare balanced rank, speed, same-currency API rates, configured quality, quota, observed rework and feasibility. The alternative scenario recomputes the forecast with an explicit Developer resource. Mission Control prepares one durable resource proposal for one remaining stage or for up to twelve remaining stages in the same mission. It compares timing, cost coverage, and quota evidence and shows the exact old and new plan digests. Approval and rejection are separate Owner actions. Approval keeps the old revision and the original estimate, updates only remaining bindings, and leaves Start or Resume as a separate action. A Developer change on a task with QC first requires an explicit Reviewer binding to preserve Reviewer independence. Unstarted Backlog tasks can use a durable allocation proposal for an exact registered profile in the same harness kind and mode. Approval binds the reviewed digest and does not start a worker.

A recorded resource failure — provider unavailable, model rejected, account unavailable, authorization expired, verified quota exhausted, shared pool unavailable, reviewer or developer blocked, execution interrupted, or resource revoked — can prepare the same proposal. The original run stays the evidence. The proposal names one eligible replacement or says that none exists. Head text can request the proposal and cannot settle it. A stale digest is refused. The approved revision does not replay a completed run. Apply rechecks the task, policy, resource and current readiness. Tasks with existing runs, profile snapshots or frozen mission authorization stay on their recovery or reauthorization path. FO-ROUTER-COMPLETE01 uses those same forecasts and the bounded allocation search. A Router recommendation still grants no execution authority. Genuine performance comparisons stay on the real-provider rule above, with a minimum of three comparable samples and separate Developer and Reviewer results. Shared quota pools are counted once. Subscription coverage and cross-currency amounts stay incomparable. Unknown quota stays Unknown.

Saving a materially changed forecast produces a new revision. Scope, structured dependencies, changed project account preferences, relevant quota observations and mission digest changes supersede affected revisions. Migration 131 retains the first eligible Developer run link, preferring a matching mission revision. Original and frozen estimates remain available in task Analytics, with interim remaining work based on the frozen scenario and completed stages. Task Analytics lists the approved resource revisions and the projected remaining duration before and after each decision alongside the original estimate, frozen estimate and actuals. Duration and cost error calculations retain the existing comparability checks.

## Portfolio planning view

FO-FORECAST-PORTFOLIO01 adds no new engine. `forecast` already returned the schedule, the pool rows and the blockers; it now also returns three read-only summaries of those same results.

**First constraint per task** (`constraints.ts`, returned as `constraints` and `firstConstraint`). For each selected task, in order: project not running, waiting for an Owner decision, waiting for a selected predecessor (`dependency`), a dependency outside the selection, a resource that is unavailable or needs preflight, a **known pool shortfall**, **Unknown capacity**, and a busy slot. The first applicable one is `first` and the rest are `also`. A task that waits on another task is therefore told apart from the task whose stage the pool cannot fund. The capacity planner now exposes each pool's `stageDemands` in charging order and its `shortfall` (known demand above the observed balance, in the pool's own unit): an exhausted pool funds no stage, and an insufficient pool funds stages until the running known demand passes the balance. `firstConstraint` is the most serious resource or capacity fact (hold, missing evidence, known shortfall, Unknown capacity, busy slot) in selection order. A pool whose status is `insufficient` means demand exceeds a known balance; the UI labels it "Known shortfall", not "Insufficient data". Unknown demand stays a separate count and is never added to known demand or treated as zero.

**Alternative comparison** (`portfolio-comparison.ts`, returned as `comparison` when `alternative` is set). The service runs the same selection and assumptions twice, without and with the Owner's explicit alternative (`save: false`; an alternative with `save: true` is refused), and lines the results up: current and proposed resource, which of harness, account, model or mode changed, the expected schedule and resource wait, bottlenecks, each pool on each side (shared pools once; known-demand difference in the pool's own unit only), cost, and the affected tasks (resource, timing or constraint changed). A difference is withheld, with a stated reason, when a side has no schedule, when the schedule rests on a `capacity` blocker (pool shortfall or unevidenced capacity), when stages have Unknown or subscription cost, or when categories or currencies differ. A completion window is shown only when the forecast produced one; otherwise the blockers are listed. Owner assumptions used by the preview are echoed so the UI labels them as assumptions.

**Recorded refusals** (`candidateRefusals`, keyed by option). A provider refusal recorded for a candidate is shown beside that option as evidence that an earlier request was refused. It is read after the estimates are built and is never an input to ranking, eligibility, selection, demand or any saved estimate.

None of this starts work, selects a resource or grants approval. The preview POST is a calculation. Applying an alternative stays the existing digest-bound proposal: "Review resource change" creates a proposal, approval binds its digest, and apply refuses a digest that no longer matches the task.

## Actuals and cost

SQLite runs, run events, employee execution provenance, mission reservations, observed practical tests, and QC reviews remain the source records. New runs retain their scope at start so moves, mutable selections, and reservation release do not rewrite attribution. Older runs can use directly linked historical employee, QC, or reservation records. Missing historical facts stay Unknown. The database records the time of subsequent Done transitions. Old Done tasks without a recorded transition remain separately counted.

A recorded provider fixture stores its token counts on the run with source `recorded-fixture`. Those counts stay visible on the task run. They stay out of genuine model rankings and company token totals. Missing token, cost, and subscription-quota fields stay null. A fixture is not converted to zero and is not labeled a real provider execution.

Analytics uses the latest recorded Done for the current completed task and counts run usage by start date through that Done cutoff. A run interval counts once toward active wall time even when agents overlap. Cumulative worker time sums separate run intervals. Created-to-Done, first-run-to-Done, Ready-to-first-run, tests, QC, and rework are displayed separately. A rework round requires a recorded failed test or Changes Requested followed by another Developer run. Run duration measures the recorded interval and can include tool waits. Human effort is Unknown.

Mission admission records transitions into dependency, queue, specialist capacity, account capacity, verified-quota, and Owner waits. Task Analytics partitions elapsed time into exclusive intervals. Runtime and observed testing take precedence over overlapping scheduler or Ready-to-start waits. Remaining time in the observed span is unclassified. The Ready-to-first-run interval provides coarse queue coverage where no more specific event was recorded. Run intervals expose the portion whose internal waiting is Unknown. No supported runtime reports an independently attributable provider waiting interval to this service. Comparable measured wait ranges are reported separately from worker calibration.

Token receipts come from the Codex exec completion event, the existing Claude bounded result, and fx per-turn telemetry. Cache-aware accounting honors source-specific field semantics. Codex resume can report thread totals, so the service withholds ambiguous resumed-run usage from additive totals. Claude cache-read and cache-write tokens are separate from uncached input. fx exposes reported counts per run, but upstream input semantics and CLI cost telemetry lack sufficient billing evidence for combined input totals or charges. [Codex exec event schema](https://github.com/openai/codex/blob/main/codex-rs/exec/src/exec_events.rs), [OpenAI token accounting notes](https://github.com/openai/symphony/blob/main/elixir/docs/token_accounting.md), [Claude prompt caching reference](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

Money stays in its original currency and evidence category. The categories are an explicit provider billing receipt, calculated API cost, subscription-covered, internal accounting, and Unknown. CLI cost telemetry stays separate from billed cost. API and subscription pricing configuration requires an explicit registered account binding. Only a revision effective before the run can calculate its cost. Missing pricing or usage remains Unknown. An actual-vs-forecast cost delta requires matching resources, a complete comparable category, and the same currency. Project and mission summaries expose coverage, filtered totals, QC rates based on genuine linked runs, completion-time distribution, and daily UTC trends.

## Forecast versus actual for one task

FO-FORECAST-ACTUAL01 adds a read-only comparison over records that already exist. It is not a new forecasting engine. `buildForecastComparison` (`src/bun/usage-analytics/comparison.ts`, types in `src/shared/forecast-comparison.ts`) is returned as `comparison` by `GET /api/usage-analytics/task` and is rendered by `ForecastActualComparison` in the task panel (compact) and in the task Analytics dialog (the dialog Analytics task rows open). It changes no QC, Done, approval, Router, budget or launch state.

**Baseline.** The baseline is the `usage_task_estimates` revision the existing run trigger froze to the task's first Developer run (`runs.usage_estimate_id`, saved at or before that run's start and not superseded). A revision saved later, including an edit made after the run, is listed as a later revision and never replaces it. A supervised Start (`approveExecution`, `launchApproved`, so board batches and Employee runs) calls `ensureBaselineEstimate` after the task's reviewed settings are applied and before `startTask`. It reuses `forecast({ save: true })` and `saveTaskEstimate`, so unchanged inputs keep their revision. It runs only for an unstarted Backlog, Inbox or Ready task and never blocks or alters a launch (best effort). A task that started with no estimate has no baseline and none is created afterwards. The comparison names the reason: not started yet, none before start, saved only after start, or superseded or planned on another harness.

**Values.** Planned ranges come from the frozen snapshot; actuals come from run, review and test records. Developer and Reviewer time use each role's own runs; the table shows cumulative agent time (summed run intervals, as the estimate does) separately from active wall-clock time (union of intervals), recorded waiting and unclassified time. A phase that never ran is Unknown, not zero. Each attempt (repeat, interrupted, failed) is listed with its own run id, status, duration and account; a run with no recorded end leaves the total partial and the difference unavailable. Money keeps its category: calculated API cost, provider-reported charge, CLI telemetry, subscription-covered runs and Unknown stay separate, and subscription quota stays Unknown without a per-run receipt.

**Differences.** A difference is shown only under the rules `taskBreakdown` already applied: a recorded Done, only genuine provider runs, the planned resources, complete durations, and one currency and category for cost. Otherwise the cell gives the reason (`DeltaReason`), for example "Not a genuine provider run". Recorded fixtures and synthetic runs therefore display actuals beside the baseline without a difference. Analytics task rows and the CSV/JSON task export carry `baselineEstimateId` (Unknown or null means no baseline).

## Tracing an amount to its records

FO-ANALYTICS-TRACE01 adds no ledger and no new accounting rule. `collectScope` (in `analytics.ts`) is the single decision of which tasks and runs a filter selects; `analytics()`, `analyticsRecords()` (`records.ts`) and every export call it, so the figures, the records behind them and the exported rows describe one set.

`GET /api/usage-analytics/records` returns one row per run in the period and scope: the project from the scope captured when the run started, the account identity captured for that run, role, run id, status, execution evidence, tokens, cost category, amount and currency, `included`, and an exclusion reason. A run counts toward amounts only when it is recorded as a genuine provider execution; synthetic and unknown-evidence runs stay visible for context with their reason (`synthetic-evidence`, `unknown-execution`). The response also carries amount buckets (one per evidence category and currency, plus count-only Unknown, subscription and excluded buckets), by-project and by-account groups, and a `reconciliation` flag that compares the buckets with `usage.costTotals`, `unknownCostRuns` and `subscriptionRuns`. Categories and currencies are never merged. A missing project or account stays Unknown (null); a later task move, account rename or resource change does not rewrite it, and a price revision only applies to runs that started after it. Names shown beside ids are display labels looked up at read time. The list is capped at 2,000 runs, newest first. The cap hides rows and never shrinks an amount: `buckets`, `counts` and the reconciliation are taken over every record in the scope, `shownBuckets` over the listed rows only, and the screen says "Listing the N most recent of M records" and separates what the listed rows add up to from the whole figure (FO-DIRECTION15).

On screen every displayed amount opens its records with a reconciliation line, a coverage line (counted runs priced, Unknown, subscription-covered, excluded), and filters by recorded project and account. A record opens the task dialog with that run highlighted. Exports: `report=runs` (CSV and JSON) holds every record including excluded rows flagged `excluded`; the task and model exports keep their columns, and the CSV preamble and JSON `coverage` now state the filter, period, eligibility rules, run counts, amount buckets and reconciliation. The task table on screen is capped at 100 rows and the task export at 500; both state the number of tasks in scope. **The scope itself reads at most 500 tasks** (the most recently updated); past that, `tasksInScopeIsLowerBound` is true, the screen shows "This filter reached more than 500 tasks", and the exports state `tasksInScope=500+ scopeTruncated=true` — the totals then describe those 500 tasks, never the full scope. The run export (`report=runs`) is not capped by the screen's 2,000: it holds every record of the scope, and its preamble and JSON `coverage` state `recordsQualifying`, `recordsExported` and `recordsTruncated`. The Overview and Costs tabs both carry the coverage line (priced / Unknown / subscription / excluded), so a partial sum never stands alone. All of it is read-only: no provider refresh, no CLI status check, no forecast or estimate change.

A hand-written run in a test database proves this arithmetic, not provider billing. Provider-reported amounts exist only for runs that store an explicit billing receipt; no supported driver writes one for a real run in this repository's tests, so genuine billing reconciliation is unverified.

## Head of PM and Full Autonomy

The Head reads the same forecasting and reporting services for usage questions within the selected scope. Exact task IDs, named projects or a named approved mission can narrow the question. The Head can explain the critical path and blockers, compare an explicitly requested concurrency against the baseline, and show a scoped read-only resource alternative. The Head can draft a scoped, exact mission resource change through its board proposal system. The card uses the same proposal and reauthorization service as Mission Control. The Owner confirms the proposal digest in its original review surface. The read-only evidence goes into the existing untrusted data section of the prompt. Forecasting adds no command, action grant, or execution authority.

Mission Control reuses the existing policy limits for launches, admission time, resource allowlists and concurrency. An expected duration and API spending budget are advisory. Selecting a hard monetary cap refuses policy activation because a verified enforcement mechanism is unavailable. An optional verified-quota rule requires fresh, positive, account-bound provider evidence before admitting a Developer or QC launch. The gate checks positive headroom across applicable verified windows and does not reserve provider quota or promise that a run will fit. Owner-reported estimates and configured thresholds do not qualify. The execution window governs admission, with already-started runs handled by the existing runtime lifecycle.

## Company analytics

The Analytics view is one report over the existing run, forecast, AccountCore, and Activity Journal records. Project, cluster, mission, specialist, role, provider, model, account, selected-task, and company filters are alternate views of that report. A run is counted once inside the selected view. Those views are not added together. A task that later moves keeps the scope stored on the run. A later genuine provider receipt uses this same run row. It is not copied into a second usage table per scope. Recorded fixtures and synthetic execution stay out of genuine token totals and model rankings. Missing money and subscription fields stay Unknown.

Calendar presets use the Owner display timezone. Stored timestamps stay epoch milliseconds. The Head's calendar answers are labeled UTC. Grouping is by day, ISO week, or month in the selected timezone. Created, running, and blocked counts come from the task registry when the filter has no specialist, provider, model, or account constraint. Started means the first run start falls in the range, including a pipeline child. Completed means the task is Done and its latest Done transition falls in the range. Usage sums still come from the bounded actuals scan. A truncated scan is labeled. The task list defaults to 100 rows and export asks for 500.

Lifecycle coverage comes only from recorded transitions and run intervals. Created-to-Done and first-execution-to-Done stay empty until a recorded Done. A running task shows partial elapsed time and does not claim completion. Inbox, Ready, and Backlog times stay Unknown when no transition was recorded. Cumulative worker time sums run intervals. Active wall time is their union. Developer, Reviewer, preparation, test, QC, rework, measured waiting, and unclassified time stay separate. An interrupted or cancelled run counts as an interruption. A succeeded run counts as a completed run.

Cost categories remain provider-billed, calculated API, subscription-covered, internal, and Unknown. An Owner-reported adjustment is a separate immutable row in `usage_cost_adjustments`. A later row can supersede an earlier one. It does not rewrite a run charge. Currencies are never added. No foreign-exchange table is stored. Missing money stays Unknown, including in export, where CSV writes the word `Unknown` and JSON writes null.

Quota history pairs compatible AccountCore observations. A reset does not create negative usage. An explicit `usage-accounting` receipt `{ quota, amount, unit }` on a genuine, non-resumed run is the only per-run subscription attribution. A pool delta with no such receipt stays unattributed. The task statement is then `Per-task subscription quota consumption: Unknown`. A receipt larger than the pool delta is not forced onto the task. Configured limits are not verified capacity. Owner-reported readings stay Owner-reported. Synthetic sources stay labeled as fixtures.

Employee and model comparisons use genuine `real-provider` history, the same rule as Router 2.0. A Reviewer participation is not an implemented task. A comparison is labeled comparable only with at least three genuine samples in one task category. Otherwise the label is insufficient data. Synthetic drivers are excluded from those rankings. Forecast training samples are completed tasks only. A running task can show interim error and is not a training sample. The original estimate is not rewritten when a mission revision or a recorded wait explains part of the delay.

Export uses the same filter, timezone, and grain as the open report. CSV and JSON include source and coverage metadata. They omit credentials, authentication paths, secrets, and prompt text. Backup copies the SQLite file, so adjustment rows travel with the existing snapshot.
