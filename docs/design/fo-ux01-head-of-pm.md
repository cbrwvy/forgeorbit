# FO-UX01 — Head of PM: плавающий главный агент

Статус: UX-концепция и поведенческий прототип. **Новой production-AI-интеграции нет**; прототип — `docs/design/prototypes/fo-ux01/index.html` (орб в правом нижнем углу, `Ctrl/⌘+J`).

## 1. Идея и границы

Head of PM — **единственная «дверь» к главному AI-агенту**, доступная с любого экрана: круглый орб 56 px поверх рабочей области; по нажатию — плавающая панель чата. Это *оболочка*, а не вторая система: панель показывает те же диалоги, те же карточки и проходит те же гейты, что уже реализованы в Project Manager (FO-005A/B/C) и Portfolio Manager (FO-008C).

Что Head of PM **не делает** (границы, не подлежащие смягчению):
- не запускает агентов и не создаёт/не назначает задачи сам — только предлагает; исполняет решение Owner через существующие карточки одобрения;
- не расширяет права (permission/approval-контракты неизменны);
- не хранит собственную «память проекта» и не придумывает статусы: ответы строятся из контекста, который сервер уже собирает (`gatherPortfolioContext`, контекст проектного менеджера);
- не отправляет сообщений в фоне: ход (turn) стартует только по Send/Retry, как сегодня.

## 2. Что в системе уже есть (основа для переиспользования)

| Нужно орбу | Уже существует | Источник |

| Карточки одобрения | `ProposalCard`, `DelegationCard`, `ExecutionCard`, `AssignmentProposals`, `EmployeeRunReviewDialog` | `components/workspace/manager/*`, `portfolio/*`, `company/*` |

## 3. Два контекста

Сегмент (`radiogroup`) в шапке панели: **Текущий проект | Все проекты**.

| | Текущий проект | Все проекты |
|---|---|---|
| Кто отвечает | Project Manager выбранного проекта (его агент, его consent) | Portfolio Manager (глобальный; Head привязан к нему) |
| Данные | IDEA/PRD/README, доска, запуски, пакеты, команда **этого** проекта | снимок портфеля: доски, запуски, пакеты, окружения, ресурсы, конфликты |
| Действия-предложения | задачи, планы, назначения, подготовка запуска | планы по портфелю, **делегирование** конкретному менеджеру проекта (отправляется только после «Одобрить») |
| По умолчанию | если открыт проект | если открыт не проект (Главная/Команда/Портфель) |
| Индикатор | чип «Проект: Atlas Billing · N задач» | чип «Все проекты (N) · M задач» |

Правила:
1. Контекст всегда **виден** (чип под сегментом + подзаголовок «контекст: …») и **озвучивается** (`aria-live` при смене).
2. Если проект не открыт, «Текущий проект» неактивен с подсказкой «Откройте проект» (не молчаливый откат).
3. Диалоги раздельны: переключение контекста не смешивает историю (в прототипе — два лога); черновик хранится по ключу контекста.
4. Переключение во время идущего хода не прерывает его; индикатор «думает» остаётся на орбе, а в панели — у соответствующего контекста.
5. Проект, исчезнувший из реестра, закрывает «Текущий проект» с сообщением (как сегодня для delegation-цели).

## 4. Состояния орба

Состояние выводится из реальных данных, не из таймеров; несколько одновременно → **приоритет сверху вниз**.

| Состояние | Условие (источник) | Вид (форма, не только цвет) | `aria-label` |
|---|---|---|---|
| **Thinking** | ход менеджера в процессе (`turn` pending/running у проектного или портфельного менеджера) | вращающееся кольцо + три пульсирующие точки | «Head of PM. Состояние: думает.» |
| **Error** | последний ход `failed`; блокировка с признаками ошибки запуска/`session-died`; ошибка загрузки контекста | красный шар, кольцо, бейдж «!» | «…Состояние: ошибка.» |
| **Needs Owner** | есть то, что ждёт Owner: ожидающие `interaction`, колонки `blocked`/`review`, pending proposals / delegations / hiring / assignment, незавершённый consent («Confirm the agent to start») | янтарное пульсирующее кольцо + числовой бейдж N | «…нужно ваше решение, N.» |
| **Working** | идут запуски (`running`), выполняется пакет/pipeline | медленное бегущее кольцо + бейдж N запусков | «…исполнители работают, N.» |
| **Idle** | ничего из перечисленного | спокойное «дыхание» (halo 6 с) | «…свободен.» |

Правила: число N считается в **текущем контексте** (проект/все); смена состояния озвучивается один раз через `role="status"`; под `prefers-reduced-motion` анимация отключена, остаются форма и бейдж; в Needs Owner/Error панель при открытии начинается со сводки «что именно ждёт» со ссылками на задачи.

## 5. Панель

Содержимое сверху вниз: шапка (мини-аватар, «Head of PM», подзаголовок-контекст, ✕) → сегмент контекста → строка контекста (чип + «какие данные читаются») → лог диалога (`role="log"`, `aria-live="polite"`) → быстрые подсказки (по контексту) → поле ввода → подвал («Enter — отправить · Shift+Enter — перенос · Esc — закрыть», «Каждое сообщение — один платный запрос выбранному агенту»).

Сообщения агента всегда несут строку **«Источники: …»** (какие данные использованы). Если данных нет — прямо «неизвестно» (по правилу портфельного менеджера: stale = unknown; % использования ≠ остаток).

### Карточка предложения (Owner gate)
Предложение (план, задачи, назначения, делегирование) рендерится существующей карточкой с янтарной полосой и подписью «Это предложение. Задачи появятся только после одобрения Owner». Кнопки «Одобрить и создать» / «Отклонить». Одобрение вызывает **тот же** endpoint, что сегодня (`…/proposals/:id/approve`, `…/delegations/:id/approve`, `…/executions/:id/approve`). В прототипе одобрение лишь добавляет демо-задачи в бэклог — AI и бэкенд не вызываются.

| Просьба Owner | Что делает агент | Где подтверждается (существующий гейт) |
|---|---|---|
| «Создай задачу/план» | `<task_proposals>`/`<plan>` | `ProposalCard` → Approve (создаёт только Backlog) |
| «Кого назначить?» | рекомендации исполнителей | `AssignmentProposals` → Approve (FO-010D; не запускает, не выбирает модель) |
| «Запусти задачу» | `<execution_proposal>` | `ExecutionCard` → «Approve & Execute» (FO-005B) |
| «Запусти пачку» | подготовка пакета | Batch approve → отдельный Start (FO-005C) |
| «Включи автономность» | не может сам | Autonomy grant — отдельное действие Owner (FO-ORCH08) |
| «Передай менеджеру проекта X» (Все проекты) | делегирование | `DelegationCard` → Approve (FO-008C) |
| «Учти эти заметки» | запрос grant | Knowledge grant на одно сообщение (FO-011E) |
| Запуск сотрудника | — | `EmployeeRunReviewDialog` (FO-010E2) |

## 6. Поведение, клавиатура, фокус

- Открыть/закрыть: клик по орбу, `Enter`/`Space` на орбе, **`Ctrl/⌘+J`** (глобально; не срабатывает поверх модального листа). Закрыть: `Esc`, ✕, повторный `Ctrl/⌘+J`.
- Фокус: при открытии — в поле ввода; при закрытии — возвращается на орб. Панель **не модальна** (`aria-modal="false"`): `Tab` выводит из неё, фон остаётся доступен; модальный лист «Новая задача» делает орб и панель `inert`.
- Сегмент контекста — `radiogroup`, `←/→` переключают (roving tabindex).
- `Enter` отправляет, `Shift+Enter` — перенос, `Enter` во время IME-ввода не отправляет.
- Положение: перетаскивание орба — привязка к ближайшему из 4 углов; с клавиатуры `Shift+Стрелки` на орбе. Угол сохраняется (`localStorage`, как `panel-collapse.ts`, читается синхронно до первого рендера).
- Сохранение контекста: выбранный контекст, угол, открыта ли панель (опционально), черновик по контексту — `localStorage`; **история диалога — на сервере** (общая с полноэкранной страницей менеджера, расхождения невозможны).
- `prefers-reduced-motion`: без `pulse/spin`, появление панели без трансформации. `prefers-reduced-transparency`: панель — сплошная `--surface`.

## 7. Нехватка места и перекрытие критичных кнопок

| Ситуация | Решение |
|---|---|
| Контент под орбом | у всех прокручиваемых областей нижний inset 96 px (в прототипе `.content`) — ни одна основная кнопка не оказывается под орбом при прокрутке до конца |
| Открыта правая панель RunPanel (её «Send» — в нижнем правом углу окна; **реальный конфликт**, виден на скриншоте `evidence/fo-ux01/audit-09-task-details-1440-dark.png`) | орб якорится к правому краю **рабочей колонки**, а не окна: смещается влево на ширину открытой панели — тем же сигналом `panelMounted`, что уже сдвигает тосты |
| Модальный диалог/лист | орб и панель `inert`/под скримом; фокус-ловушка диалога не меняется |
| Окно < 760 px | панель — нижний лист на всю ширину (`max-height 78vh`), орб скрывается, пока лист открыт (не перекрывает «Отправить»); открытие — через орб или `Ctrl/⌘+J` |
| Окно < 480 px | орб 48 px, панель на весь экран |
| Пользователь мешает орб | перетащить/`Shift+Стрелки` в другой угол; опция «Скрыть орб» в Settings (⌘J при этом остаётся) |
| Нет места для панели 420×640 | высота ограничена `min(640px, 100vh − 168px)`, ширина `min(420px, 100vw − 24px)`; лог прокручивается, композер всегда виден |

Проверено в прототипе (`verify.mjs`): отсутствие горизонтального переполнения на 1440/1100/820/600/420 px; орб не пересекается с кнопкой «Отправить» ни при одной ширине; на ≤ 760 орб скрыт при открытой панели.

## 8. Пользовательские потоки

1. **Спросить по проекту.** Орб → панель (контекст = проект) → «Что блокирует проект?» → ответ из доски со ссылкой на задачу → клик по задаче открывает детали.
2. **Обзор всех проектов.** `←/→` на сегменте → «Все проекты» → «Сводка по всем проектам» → список по проектам; по строке — переход в проект.
3. **Поручение → задачи.** Ввод «Добавь экспорт в CSV…» → ответ-предложение (карточка) → Owner правит/одобряет → задачи в Backlog → (отдельно) «Запустить» с подтверждением.
4. **План работ.** «Составь план» → `<plan>` + карточка → одобрение → «План и очередь».
5. **Рекомендации исполнителей.** «Кого назначить?» → список с оговоркой «рекомендация; лимиты неизвестны» → кнопка «Создать предложение назначения» (не назначение).
6. **Ошибки и блокировки.** Орб в Error/Needs Owner → панель открывается сводкой → переход к задаче/«Нужно вам».
7. **Нет агента / нет consent.** Панель показывает то же, что сегодня Manager: «Confirm the agent to start» + pre-flight; Send недоступна с видимой причиной.
8. **Ошибка хода.** Сообщение остаётся, появляется «Повторить» (как `manager-retry`); орб — Error; повторная отправка безопасна (одно сообщение — один ход).
9. **Узкое окно.** Лист снизу; закрытие `Esc`/✕ возвращает фокус на орб (или на кнопку ☰/«+ Новая задача», если орб скрыт).

Критерии приёмки PM01: ни одного нового пути запуска/создания/назначения без существующего гейта; история в орбе и на странице менеджера **идентична**; проект вне реестра/без агента даёт понятное состояние, а не пустую панель; `bun run typecheck`, целевые unit/e2e зелёные.

## 10. Риски

| # | Риск | Смягчение |
|---|---|---|
| H1 | Две поверхности одного диалога → гонки отправки | один ход на менеджера уже обеспечен сервером (409); UI обновляется через общие события, `createLatestLoader` |

## 11. Что согласовать с Owner

1. Контексты **Текущий проект / Все проекты** и их маппинг на Project Manager / Portfolio Manager — подходит ли?
2. Должен ли орб быть всегда видимым, или с опцией «скрыть» (⌘J остаётся)?

5. Нужен ли агрегирующий `GET /head-of-pm/summary` (чуть больше backend) или клиент собирает состояние из существующих событий?
6. Положение по умолчанию (правый нижний) и «липкость» между сессиями.
7. Можно ли в панели одобрять предложения inline, или всегда открывать полную карточку на странице менеджера?
