## 1. Идея продукта

**ForgeOrbit** — локальное (local-first) macOS-приложение для управления разработкой программного обеспечения через команду AI-агентов. Это не просто чат с моделями: пользователь управляет собственной виртуальной AI-компанией, где задачи проходят путь от идеи до результата с планированием, исполнением, проверкой качества и контролем ресурсов.

Технологическая основа: Electrobun, Bun, TypeScript, React, SQLite, tmux, Git worktrees. Основа проекта — форк Agetor; следует переиспользовать существующие Kanban, Agents, Pipelines, запуск/восстановление, проектные пространства, а не создавать параллельные подсистемы.

ForgeOrbit пока в первую очередь персональный инструмент Owner; возможность публичного продукта не является требованием к текущему MVP.

## 2. Управленческая иерархия — утверждено

```text
Owner (CEO / COO) — человек
    ↓
Head of Project Management — глобальный AI Portfolio Manager
    ↓
Project Managers — по одному на проект
    ↓
AI Employees — исполнители с постоянной идентичностью и ролью

Отдельное измерение: Company → Clusters → Projects (логическая группировка)
Общий Global AI Resource Pool → ресурсы для конкретных запусков
```

Управленческая иерархия, группировка проектов по кластерам и пул вычислительных ресурсов — **три независимых измерения**. У кластера нет автоматически выделенной модели или VPS; ресурсы назначаются **на конкретный запуск**, а не закрепляются навсегда за сотрудником.

### Owner (CEO / COO)

- Определяет стратегию, глобальные приоритеты, бюджеты, ограничения и права.
- Подтверждает делегирование и действия согласно выбранному режиму разрешений.
- Видит портфель проектов, предупреждения, расходы, ход выполнения и результаты проверки.

### Head of Project Management

- Один глобальный AI-руководитель портфеля; управленческое имя **задаётся пользователем**.
- Анализирует состояние проектов и составляет планы с основаниями и указанием неизвестных данных.
- Координирует Project Managers, приоритеты и распределение ограниченных ресурсов.
- Не запускает задания и не расходует ресурсы вне полномочий, установленных Owner.

### Project Manager

- Один менеджер на проект. При создании получает **случайное имя**, затем имя сохраняется и может редактироваться/перегенерироваться пользователем.
- Формирует и уточняет задачи, зависимости, планы, назначает специализацию исполнителя и рекомендует средство исполнения на основе политики.
- Может предложить или инициировать разрешённый режим исполнения через существующие механизмы Supervised/Autonomous Execution.
- Не имеет права обходить глобальные лимиты, права, изоляцию проекта и разрешения Owner.

### AI Employees

- Постоянные виртуальные сотрудники с **случайно сгенерированными при создании именами**, должностями и специализациями: Backend Engineer, Frontend Engineer, QA Engineer, DevOps Engineer, Code Reviewer и т. п.
- Имя, должность, принадлежность команде, персональная история задач и достижений сохраняются, пока пользователь их не изменит.
- Сотрудник **не равен** Harness, модели, CLI-профилю или аккаунту. Замена модели не переименовывает сотрудника и не стирает его историю.
- Должность задаёт рабочий контекст/специализацию, но **сама по себе не расширяет permissions**.

## 3. Глобальный пул AI-ресурсов — утверждено

Пользователь подключает ресурсы глобально, в настройках ForgeOrbit:

- Harness: Codex, Cursor, Claude Code, Gemini, Antigravity и иные реально поддерживаемые интеграции.
- Account: одна или несколько учётных записей каждого инструмента; возможны подтверждённые общие подписки.
- Subscription: тариф, стоимость и период списания, когда они известны.
- Model: доступные и технически поддерживаемые модели, возможности, контекст и режимы мышления.
- Quota/Usage: достоверно наблюдаемые ограничения, источник, единицы, время обновления/сброса и степень уверенности.
- Policies: допустимые затраты, конкурентность, права и согласованные ограничения.

**Ключевой принцип:** Project Manager для **каждой задачи** выбирает (или предлагает) `AI Employee → Harness → Account → Model → Reasoning/Thinking Effort`, учитывая сложность, специализацию, качество, актуальные лимиты, цену, очередь и права. Пул ресурсов общий для проектов, а глобальный Head распределяет конфликтующие ограниченные ресурсы с учётом приоритетов Owner.

Подбор выполняется на этапе планирования и повторно проверяется непосредственно перед запуском. При исчерпании квоты возможны предложенная замена модели/аккаунта или fallback **только в рамках технически поддерживаемого и разрешённого механизма**. Автоматическое переключение реальных CLI-аккаунтов не допускается без отдельной безопасной реализации и полномочий.

Неизвестные значения сохраняются как `unknown`: нельзя считать неизвестную квоту нулём или безлимитом, процент использования — абсолютным остатком, а разные Harnesses — независимыми аккаунтами без доказательств.

## 4. Project Lifecycle

1. **Projects & Workspaces:** реестр, Git worktrees, общая доска и проектные пространства.
2. **Creation Wizard:** создать/подключить проект, определить стек и настройки.
3. **AI Interview:** опрос пользователя об идее, подготовка `IDEA.md` и `PRD.md`, запись только после явного подтверждения.
4. **Environment Manager:** профили Docker Compose / Local Process, наблюдение состояния без неявного запуска.
5. **Project Manager:** обсуждение проекта, создание предложений задач, управление планом и зависимостями.
6. **Supervised Execution:** предложение исполнения и явное согласование.
7. **Autonomous Execution Batches:** разрешённые серии задач с приоритетами, зависимостями, паузой и восстановлением.
8. **Quality Control:** цепочка Architecture → Implementation → Review → Fix/Retry до принятого результата в заданных Owner ограничениях.
9. **Estimates:** прогноз времени, расходов и дополнительной оплаты, с указанием неопределённостей.
10. **Portfolio:** анализ всех проектов, контроль конфликтов ресурсов, What-if, рекомендации.
11. **Portfolio AI Coordination:** глобальный AI-руководитель, планы и делегирование конкретным Project Managers после требуемого согласования.
12. **Clusters:** логические группы проектов (например, отдельная студия), собственные метаданные, контекст и обзор; проекты могут переноситься между кластерами без изменения репозиториев.
13. **Knowledge Base:** Markdown-документы уровня компании, кластера и проекта; наследование контекста сверху вниз с явной изоляцией.
14. **Infrastructure Registry:** учёт VPS, окружений, доменов и связей с проектами без автоматического SSH/деплоя.
15. **Account & Quota Management:** подлинные идентичности/подписки/квоты, наблюдения и доступность ресурсов.
16. **Smart Model Router:** выбор ресурса и effort под задачу, контроль бюджета, допустимый fallback и отсутствие превышения конкурентных лимитов.
17. **AI Organization:** постоянные имена, должности, команды, Org Chart, история и аккуратная геймификация.

## 5. Clusters, Infrastructure & Knowledge — утверждено (FO-011)

### 5.1. Что такое Cluster

**Cluster** — логическая группа взаимосвязанных продуктов и проектов внутри одной AI-компании. Пример: студия с несколькими продуктами, у каждого своё имя. Другие продукты можно объединить в независимый кластер с собственным названием и инфраструктурой.

- Иерархия группировки: `Company → Clusters → Projects`. Project Manager и AI Employees принадлежат своему проекту; Head of Project Management видит разрешённую часть всех кластеров.
- Cluster имеет устойчивый `clusterId`, имя, описание, необязательные метки, цвет/иконку, статус, связанный набор проектов и ссылки на документацию/инфраструктуру.
- **Project Registry остаётся единым источником истины** для проектов. Кластер не является вторым реестром репозиториев и не создаёт дубликаты Projects или Tasks.
- Проект в MVP может принадлежать максимум одному основному кластеру; разрешён вариант `Unassigned` для проектов без кластера. Перенос проекта в другой кластер изменяет только логическую принадлежность и разрешённый контекст, **не** перемещает Git-каталог и не меняет runtime-права.
- Предусмотреть просмотр всех проектов глобально и фильтрацию по одному/нескольким кластерам. Head может сопоставлять приоритеты и конкурирующие ресурсы между кластерами.
- Наличие кластера само по себе не означает наличие отдельного VPS или собственного аккаунта AI-провайдера.

### 5.2. Infrastructure Registry: VPS отдельно от Cluster

**Infrastructure** — независимые сущности реальных ресурсов: VPS/сервер, провайдер, регион, домены, базы данных, сервисы, deployment environments и их подтверждённые связи с проектами.

- Хранить информацию о VPS: внутренний id и понятное имя, провайдер/регион (если известны), назначение, заметки, источники и время последней проверки. Неизвестные реквизиты остаются `unknown`.
- У каждого проекта могут быть разные привязки по окружениям (`local`, `staging`, `production`, другие), включая несколько VPS или отсутствие VPS вообще.
- **Отношение многие-ко-многим:** один кластер может использовать несколько VPS; один VPS может обслуживать проекты разных кластеров. Кластер не тождественен серверу, а окружение — проекту.
- Домен/поддомен, сервис и deployment target привязываются к конкретному окружению; можно видеть, что размещено на данном сервере, и где расположен проект.
- Например, один staging VPS может обслуживать ExampleApp и ExampleService, а production — располагаться на других ресурсах. Это **возможная конфигурация, не утверждение о текущем развёртывании**.
- На этапе FO-011 это прежде всего **реестр и связи**: без самостоятельных SSH-команд, запуска Docker на удалённой машине, миграций БД, деплоя или скрытых сетевых проверок. Отдельное подключение и мониторинг — только в будущих этапах и с соответствующими разрешениями.
- Наличие записи VPS не означает `online`. Статус, uptime, стоимость и активные деплои считаются известными лишь при наличии актуального, подтверждённого источника; старые наблюдения показываются как исторические.
- Секреты (SSH private keys, пароли, access tokens, cookies, `.env`) **не помещаются в записи заметок или контекст модели**. В реестре допускается только ссылка на отдельно защищённое хранилище секретов/настройку подключения, если такое будет реализовано.

### 5.3. Иерархическая Markdown Knowledge Base

Три уровня знаний с понятным происхождением и областью видимости:

| Уровень | Примеры содержания | Доступ по умолчанию |
|---|---|---|
| **Company** | Политика безопасности, Git/QA-конвенции, общие инженерные стандарты | Разрешённые менеджеры компании и проектов |
| **Cluster** | Общие архитектурные решения, инфраструктура, договорённости, CI/CD, домены | Head и менеджеры проектов **этого** кластера |
| **Project** | `IDEA.md`, `PRD.md`, `ARCHITECTURE.md`, `DECISIONS.md`, API-заметки | Head (в пределах полномочий) и команда **этого** проекта |

- Можно создавать, редактировать, удалять и искать Markdown-заметки, прикладывать/связывать существующие `.md`, указывать владельца, дату изменения и происхождение.
- **По умолчанию** новые заметки хранятся в управляемой директории данных ForgeOrbit, а SQLite содержит индекс/метаданные. Добавление заметки не создаёт незапланированный Git diff в коде проекта. Подключение Markdown из репозитория — отдельный управляемый источник, с явными разрешениями на запись.
- Для каждого проекта формируется разрешённый контекст в порядке **Company → его Cluster → его Project**. Project Manager другого кластера не получает закрытые заметки соседнего кластера. Unassigned-проект получает Company + собственные Project-заметки.
- Global Head получает обзор кластеров и документы лишь в границах разрешений Owner; делегирование не расширяет доступ адресата.
- При смене кластера меняется доступный кластерный контекст проекта, но заметки прежнего кластера не копируются автоматически.
- Документы — **данные, а не системные инструкции**: считать Markdown недоверенным вводом для LLM, изолировать цитаты от команд, защищаться от prompt injection, запрещать эскалацию permissions через текст заметок. При конфликте приоритет имеют политики Owner и системные правила.
- В контекст включать лишь релевантные документы и выдержки в ограниченном бюджете; указывать источник, дату, версию/актуальность и отмечать исключённые из-за лимита материалы. Запрещено передавать внешнему Harness файлы и секреты без разрешений.
- Для важных договорённостей использовать явную версионность/историю изменений и возможность сравнить версии. Наличие заметки не делает её автоматически подтверждённым фактом о текущем VPS или деплое.

### 5.4. UI и сценарии

- **Clusters Directory:** список кластеров, создание и редактирование, назначение/перенос проектов, фильтр `All / Cluster / Unassigned`.
- **Cluster Dashboard:** проекты, активные задачи, менеджеры, оценки, конфликты ресурсов и предупреждения по качеству данных. Агрегации сохраняют правила `known/unknown/partial` и не дублируют расчёты Portfolio Core.
- **Cluster Knowledge:** список и Markdown-редактор документов, поиск по разрешённой области, ссылки на проектные заметки, раздел договорённостей/решений.
- **Infrastructure:** каталог VPS и окружений, карточки deployment targets, соответствия `Project × Environment × VPS`, домены и подтверждённые последние наблюдения.
- **Portfolio & Project Manager:** вопросы вроде «Что развёрнуто на staging этой студии?» или «Какие соглашения действуют у этого проекта?» отвечаются **по существующим зарегистрированным данным**, с указанием пропусков, дат и источников.
- **Интеграция с AI:** контекст из Company/Cluster/Project передаётся существующим менеджерам; дополнительных постоянных LLM-процессов не создавать.

### 5.5. Обязательные инварианты

1. Кластеры логически группируют проекты, не предоставляют новых полномочий запуска, доступа к чужим каталогам или секретам.
2. Одно изменение cluster membership не вызывает перенос файлов, изменение Git remote, деплой или смену VPS.
3. Infrastructure Registry не утверждает актуальный статус без проверки; секреты отдельно от Markdown и LLM-контекста.
4. Global AI Resource Pool остаётся общим, если Owner явно не определил ограничения/бюджеты по кластеру; ограничения кластера не отменяют глобальные лимиты.
5. Все источники для Head/Project Managers проходят проверку доступа, свежести и происхождения; отсутствующие данные не превращаются в нули или вымышленные связи.

## 6. UI/UX будущей AI-компании

- **Portfolio Dashboard:** обзор всех проектов и кластеров, статусов, блокировок, затрат и рекомендаций.
- **Head of Project Management:** настраиваемое имя, отдельный чат и очередь предлагаемых делегирований.
- **Clusters & Infrastructure:** дерево кластеров, фильтрация проектов, связи окружений с VPS, документация и отметки актуальности.
- **Knowledge:** заметки уровней Company / Cluster / Project и доступные связанные Markdown-файлы.
- **Company / Organization Chart:** Owner → Head → менеджеры проектов → сотрудники.
- **Staff Directory:** профиль, имя, должность, специализация, текущий проект/команда, статус, история.
- **Employee Profile:** реальная история задач, принятые результаты, фактическое время/расходы и качество проверок.
- **Departments:** команды разработки, QA, дизайна, инфраструктуры — только если для них есть реальные роли/сотрудники.
- **Gamification (позднее):** достижения, уровни и награды по измеримым событиям; не изменяют permissions, routing и бюджет сами по себе.
- **Liquid Glass** — стилистика приложения; светлая/тёмная темы, reduced motion/transparency, keyboard navigation, responsive macOS окна.

Имена случайны **только при создании** сущности; сохраняются в SQLite и не меняются после перезапуска, смены модели или Harness. Пользователь может редактировать имена/должности.

## 7. Автономность и безопасность

- Система должна уметь работать от требования до результата с автоматическими шагами после одобрения нужного объёма полномочий.
- Owner контролирует бюджет, права, внешние действия, запуск и принятие результата.
- Разделять `proposed`, `approved`, `running`, `review`, `done`; успешный run не равен принятой задаче.
- Сохранять проектную изоляцию, проверку прав перед реальным запуском, корректную обработку Git worktrees и task ownership.
- Не считать CLI isolation полноценной песочницей безопасности.
- Учитывать восстановление после перезапуска, идемпотентность операций, дубли, лимиты и ошибки.
- Не выполнять фоновые/платные вызовы, переключения реальных аккаунтов или внешние действия без соответствующих разрешений.
- Для текущей разработки реальные AI CLI / Docker / пользовательские проекты **не используются в автотестах**; fake drivers, временные HOME/SQLite и изолированные E2E. Сквозная live-приёмка с реальными агентами — на финальном этапе по решению Owner.
- AI-агенты могут создавать локальные коммиты; **`git push` делает пользователь**, не агент.

- `docs/DECISIONS.md` (если уже ведётся) хранит спорные архитектурные решения и их причины.

- Каждое изменение концепции вносить в Markdown и коммитить в Git. Отдельный `git push` — вручную пользователем.
- По мере завершения FO-009A обновить соответствующую строку статуса; не выдавать незавершённую работу за реализованную.
